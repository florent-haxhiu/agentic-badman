# AgentCore Observability

Your agents are making decisions every tick — positioning, passing, shooting, marking. But right now, you're watching the match like a fan in the stands. You can see what happened, but not why . Why did your defender leave the striker unmarked? Why did the midfielder ignore an open teammate? AgentCore Observability puts you in the dugout with a tablet — full visibility into what every player was thinking, how long each decision took, and where things went sideways.
The good news: observability is already enabled for all sample agents. Every `.bedrock_agentcore.yaml` includes `observability: enabled: true` , and every `requirements.txt` includes `aws-opentelemetry-distro` . You don't need to deploy anything new. Just open CloudWatch and start exploring.
[What's Already Collected](#what's-already-collected)
Here's the good part. You don't need to instrument anything. AgentCore automatically collects the following for every agent invocation:
| Data | What it shows |
| Session metrics | Invocation count, latency, errors, throttles per agent |
| Traces | Full execution path of each request — from game state input to command output |
| Spans | Individual operations within a trace (LLM call, tool invocation, memory retrieval) |
| Application logs | Runtime errors, agent startup, fallback activations |

If you deployed Memory or Gateway agents, you'll also see:

- — Tool invocations ( , , etc.) with per-tool latency

[Step 3: Investigate a Trace](#step-3:-investigate-a-trace)
Traces show the full execution path of a single agent invocation — from receiving the game state to returning a command.
1. In the CloudWatch console, choose from the left navigation
2. Navigate to
3. Filter by service name or agent name
4. Choose a trace to view the detailed execution graph and timeline
Detailed spans (LLM calls, tool invocations, memory operations) appear after real match invocations. Sandbox tests may only show 1-2 basic invocation spans. Play a match first to see the full trace waterfall.
After a match, you'll see traces with spans like these:

```
Agent Invocation (total: ~800ms) ├── State Summarization (~5ms) ├── LLM Call - Nova Micro (~700ms) └── Response Parsing (~2ms)
```

For a memory agent, you'll see additional spans:

```
Agent Invocation (total: ~1200ms) ├── Memory Retrieval - ListEvents (~150ms) ├── State Summarization (~5ms) ├── LLM Call - Nova Micro (~800ms) ├── Response Parsing (~2ms) └── Memory Store - CreateEvent (~100ms)
```

For a gateway agent, tool calls appear as spans:

```
Agent Invocation (total: ~2000ms) ├── State Summarization (~5ms) ├── LLM Call - Nova Micro (~500ms) ├── Gateway Tool - calculate_pass_options (~200ms) ├── LLM Call - Nova Micro (~400ms) └── Response Parsing (~2ms)
```

[Step 4: Check Agent Logs](#step-4:-check-agent-logs)
Logs are useful for debugging specific errors — like why an agent returned a fallback command instead of an LLM response.
1. Open the [CloudWatch console](https://console.aws.amazon.com/cloudwatch/)
2. In the left navigation pane, expand and choose
3. Use the search field to find the log group for your agent. AgentCore creates log groups following this naming pattern:
Runtime logs (stdout/stderr output and OTEL structured data):
- :
- : Runtime errors, application logs, debugging statements (e.g., and output), OTEL execution details, error tracking, and performance data
- : No additional code required — generated by ADOT instrumentation
- : Includes correlation IDs linking logs to relevant traces
Search for
`/aws/bedrock-agentcore/runtimes/`
in the Log groups search field to find all your agent log groups at once.
Common things to look for:
| Log pattern | What it means |
| LLM parse failed, using fallback | The LLM returned invalid JSON — the agent fell back to rule-based commands |
| agent error | An unhandled exception occurred during invocation |
| AccessDeniedException | Missing IAM permissions (e.g., Memory or Gateway access) |
| Timeout | The agent took too long — the match server moved on without waiting |

You're all set.
Use these observability tools during matches to debug bad decisions, spot timeouts, and understand how your agents think. The more matches you play, the more data you'll have to work with.
